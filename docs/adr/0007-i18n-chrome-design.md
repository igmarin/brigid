# ADR 0007: i18n Chrome Design for Tutorial Localization

## Status

Accepted

## Date

2026-07-25

## Context

The tutorial output has two distinct kinds of text:

1. **Generated content** — chapter titles, abstraction descriptions, file
   paths, code identifiers, evidence footers. These are produced by the LLM
   and are inherently language-specific (the LLM is prompted in the target
   language via `--language`).
2. **Chrome strings** — fixed headings, labels, and the attribution footer
   that appear in the index and around generated content. Examples:
   "Chapters", "Setup Guide", "Architecture Overview", "Learning Path",
   "Generated by decon".

Issue #137 (M4-I18N-1) requires that chrome strings be localized independently
of the LLM. Relying on the LLM to translate fixed UI strings is unreliable
( inconsistent translations, hallucinated labels) and wastes token budget on
deterministic text.

The Python reference implementation used a `i18n_chrome` function with a
hardcoded dictionary. The Rust port needs a clean, extensible, and testable
equivalent.

### Constraints

- Chrome strings must be deterministic and testable (no LLM dependency).
- Adding a new locale should be a small, localized change — not a sweeping
  refactor.
- Some chrome strings appear inside Mermaid diagram labels, which do not
  support accented characters reliably across renderers. The Spanish
  "Chapters" heading must use the accent-free "Capitulos" (not "Capítulos")
  when used in Mermaid contexts.
- Unknown locale input (e.g. `--language fr`) must not crash; it should fall
  back to English.
- The locale code must round-trip through serde (for `RunConfig` serialization
  in checkpoints).

## Decision

Implement a generic localization framework in `decon-core::i18n` with two
types: `Locale` (an enum) and `ChromeStrings` (a struct of `&'static str`
fields).

### `Locale` enum

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum Locale {
    En,
    Es,
}
```

- Wire format is the lowercase ISO-ish code (`"en"`, `"es"`) via serde rename.
- `Locale::parse(s)` is case-insensitive and returns `Option<Locale>`.
- `Locale::parse_or_default(s)` falls back to `Locale::En` for unknown input.
- `Display` impl writes the canonical code (`"en"` / `"es"`).

### `ChromeStrings` struct

```rust
pub struct ChromeStrings {
    pub chapters_heading: &'static str,
    pub setup_link: &'static str,
    pub overview_link: &'static str,
    pub evidence_label: &'static str,
    pub key_files_label: &'static str,
    pub learning_path_heading: &'static str,
    pub system_map_heading: &'static str,
    pub concept_map_heading: &'static str,
    pub how_to_use_heading: &'static str,
    pub attribution: &'static str,
}
```

All fields are `&'static str`, so the struct is `Copy` and cheap to pass
around. `ChromeStrings::for_locale(locale)` returns the appropriate struct via
a match expression.

### Adding a new locale

Adding a locale (e.g. French) requires exactly two changes:

1. Add a `Fr` variant to `Locale` with its serde rename and `parse`/`as_str`
   match arms.
2. Add a `Locale::Fr => Self { ... }` arm in `ChromeStrings::for_locale`.

No trait implementations, no registration, no macro — the compiler enforces
exhaustiveness via the match.

### Mermaid safety

`chapters_heading` for Spanish is "Capitulos" (no accent), not "Capítulos",
because this string is used inside Mermaid flowchart labels. Accented
characters break Mermaid rendering in some downstream tools (GitHub, VS Code
preview). See `docs/best-practices.md` §13 for the Mermaid-no-accents rule.

Other Spanish strings (`setup_link`, `overview_link`, etc.) use accents
normally because they appear in Markdown headings, not Mermaid labels.

## Alternatives Considered

### Use a trait-based approach (`trait ChromeStrings { fn chapters_heading(&self) -> &str; }`)

- **Pros**: Object-safe; could support dynamic dispatch and external locale
  plugins.
- **Cons**: Over-engineered for a fixed set of strings. A trait + impl per
  locale is more code than a struct + match. Dynamic dispatch adds indirection
  for no benefit when the locale set is small and compile-time known.
- **Rejected**: Premature abstraction.

### Use a `HashMap<&str, &str>` per locale (dictionary approach, like Python)

- **Pros**: Familiar pattern; easy to load from a file.
- **Cons**: Loses type safety — typos in keys are runtime errors, not compile
  errors. No exhaustiveness checking when adding a new string. Allocates a
  HashMap for data that is fundamentally static.
- **Rejected**: The struct approach gives compile-time field checking and zero
  allocation.

### Use `fluent` or another i18n framework

- **Pros**: Industry-standard; supports pluralisation, gender, ICU formatting.
- **Cons**: Massive dependency for ~10 fixed strings. The chrome strings are
  simple labels with no pluralisation or formatting needs. Adds a build step
  (`.ftl` files) and runtime locale resolution.
- **Rejected**: Disproportionate complexity for the problem at hand.

### Localize chrome via the LLM prompt

- **Pros**: Zero code; the LLM handles everything.
- **Cons**: Non-deterministic — the LLM may translate "Chapters" differently
  in the index vs. a cross-reference. Wastes tokens on fixed strings. Cannot
  guarantee Mermaid-safe accent-free strings.
- **Rejected**: Violates the determinism requirement for chrome strings.

## Consequences

- **Positive**: Chrome strings are deterministic, testable, and compile-time
  checked. Adding a locale is a small, mechanical change.
- **Positive**: Unknown locales fall back to English gracefully — no panic,
  no error, just a sensible default.
- **Positive**: Zero allocation — `ChromeStrings` is `Copy` with `&'static str`
  fields.
- **Positive**: Mermaid safety is enforced by choosing the accent-free variant
  for the `chapters_heading` field.
- **Negative**: Adding a new chrome string requires updating the struct, both
  locale arms, and all tests. This is intentional — it forces explicit
  consideration of each new string across all locales.
- **Negative**: The struct is not extensible at runtime (no plugin system).
  If third-party locale packs are needed in the future, a trait-based approach
  would be revisited.
